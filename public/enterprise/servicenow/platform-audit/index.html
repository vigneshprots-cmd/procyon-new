Our view

Upgrades are where customization sends the bill.

An instance does not decay all at once. Each request handled with a script instead of configuration, each base record edited in place, adds a little to what the next upgrade has to work around.

With two family releases a year, that cost arrives on a schedule. Teams start deferring upgrades, new capabilities never reach users, and the platform owner ends up defending the licence renewal instead of the roadmap.

  • Base records edited in place

    Out-of-box business rules, script includes, UI policies and forms changed directly. The upgrade skips them, so they keep old behaviour and miss fixes, and the skipped list is rarely reviewed.First move: a decision on every skipped record: revert, merge or keep

  • Scripts that redo the platform

    Client scripts and business rules re-implementing assignment rules, data policies, SLAs or approvals that ServiceNow already provides. They run on every form load and every save.First move: an inventory of custom scripts against out-of-box features

  • A CMDB that fails its own health score

    Duplicate and stale CIs from imports that bypass identification and reconciliation, classes with no owner, and services modelled outside CSDM. Every process that reads the CMDB inherits the errors.First move: CMDB Health completeness, correctness and compliance as a baseline

  • Integrations nobody owns

    Scripted REST calls, transform maps and MID Server jobs written by people who have left. They fail quietly and users find out first.First move: an integration register with an owner and an alert for each

What gets audited

Six areas, measured in the instance, not in interviews.

Interviews explain why things were built. The instance shows what was built. The health check uses both, and every finding carries the record it came from.

CMDB integrity
Duplicate, stale and orphaned CIs, identification rules, class ownership, and the business services that depend on bad records.
Workflow configuration
Broken flows, legacy workflows still running, and the workarounds the service desk built around the original gaps.
Integration health
Failing syncs, MID Server issues, credentials held in scripts and undocumented connections through IntegrationHub.
Licensed utilization
What was bought, what is used, and which modules are costing money without users.
Upgrade readiness
Skipped records from recent upgrades, customized base records, and how far the instance sits from current.
Code quality and testing
Instance Scan findings, global business rules, hard-coded sys_ids and how much is covered by the Automated Test Framework.

Revert, rebuild or keep

Not every customization is debt. Each one gets a decision.

Some customizations encode a real business rule and should stay, properly built. Most of the ones found in an audit fall into a few patterns, and each pattern has a usual answer.

The patternWhat it costsThe usual decision

Base systemEdited out-of-box records

Skipped on every upgrade, so fixes and new features in that record never arrive.

Revert to baseReapply any genuine requirement as configuration or a separate, documented extension.

Client sideClient scripts querying the server

Synchronous lookups on form load that slow every agent, every ticket, all day.

RebuildUI policies or data policies where possible, asynchronous calls where code is still needed.

Server sideBusiness rules duplicating platform features

Two mechanisms setting the same field, in an order nobody can predict after an upgrade.

RetireUse the assignment rule, SLA definition or approval the platform already provides.

Data modelCustom tables beside CMDB classes

Assets and services held outside the CMDB, invisible to change impact and to Discovery.

MigrateMove the data into the matching CSDM class with identification rules in place.

WorkflowLegacy workflows and hard-coded IDs

Logic that breaks when a group, user or record is renamed, and is hard to test.

Rebuild in Flow DesignerStore references in system properties and cover the flow with automated tests.

How it runs

A typical eight weeks, each phase signed off.

Fixed scope and a fixed SOW. The instance is ready for the next family release and for new modules or Now Assist at the end.

Asked before a ServiceNow health check.

What does a ServiceNow platform health check cover?

CMDB integrity, workflow configurations, integration health and licensed utilization. Every broken flow, orphaned record and workaround is documented and ranked by business impact.

How long does the health check take?

A typical health check runs 2 to 3 weeks and ends with a prioritized remediation plan. There is no commitment to additional work.

How long does tech-debt removal take?

A structured tech-debt removal typically takes about eight weeks, including the health check, on a fixed SOW.

Why audit before adding new modules or Now Assist?

New modules and AI depend on the CMDB and workflows underneath. Building on broken data multiplies the problems, so the foundation is fixed first.

How is the clean-up priced?

On a fixed SOW with transparent deliverables and technology costs passed through at cost, with zero markup.
