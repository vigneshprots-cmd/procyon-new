Our view

Integration estates fail at the seams nobody owns.

The Salesforce team owns Salesforce. The SAP team owns SAP. The interface that moves an order between them is owned by whoever built it, and that person left two years ago. When it fails, both teams are sure the problem is on the other side.

Good integration architecture is mostly about that seam: a published contract for what crosses it, an owner who answers for it, and monitoring that tells the owner first. The tooling matters less than the discipline, though the right tooling makes the discipline cheaper.

  • Point-to-point everywhere

    Every new system gets its own direct connection to Salesforce and the ERP. Change a field in one and three others break.First move: reusable system APIs in front of each core system

  • Batch where events belong

    An order, payment or status change reaches the other systems on a nightly job, so customers hear about it before the account team does.First move: publish the changes many systems react to as events

  • No owner, no contract

    Five teams have built five versions of the customer API. None is documented, so the sixth team builds its own.First move: OpenAPI contracts, versioning rules and a developer portal

  • Monitoring by complaint

    An interface fails or slows down and the first alert is a customer or a finance close that does not balance.First move: alerts per interface, routed to its owner

The model

Three API layers and an event backbone, shared by every team.

The API-led pattern MuleSoft popularized works on any integration platform. Each layer changes for a different reason, so a change in one does not ripple through the others.

  • System APIs.One per core system: SAP, Oracle, NetSuite, Workday, Salesforce, ServiceNow. They hide the system's quirks, so replacing the ERP means rewriting one API, not every integration.
  • Process APIs.Business logic that spans systems, such as order to cash or hire to provision. Reused by every channel that needs it.
  • Experience APIs.Shaped for one consumer: the portal, the mobile app, an AI agent. Thin, and cheap to change when the front end does.
  • Events.Orders, payments and status changes published once on Kafka, EventBridge or Pub/Sub. Each system subscribes to what it needs, with retries and dead-letter handling.

APIs suit request and response, such as a credit check before a quote. Events suit changes many systems must react to, such as a new order. Most estates need both, and the review decides the pattern per flow.

Asked before untangling an integration estate.

Which integration platforms does Procyon work with?

MuleSoft, Boomi, Workato, Azure Integration Services and AWS AppFlow and EventBridge. The recommendation follows the existing estate, skills, security needs and cost model, not vendor preference.

Is API-led or event-driven integration better?

Most enterprises need both. APIs suit request-and-response needs such as checking credit before a quote. Events suit changes many systems must react to, such as a new order or payment. The architecture review decides the pattern per flow.

How is point-to-point integration kept from coming back?

Through a reference architecture with reusable system, process and experience APIs, published standards, a developer portal and governance on every new connection.

Can legacy mainframes and EDI partners be integrated?

Yes. B2B and EDI integration covers trading partner onboarding over EDI, AS2 and SFTP, and legacy systems are wrapped in APIs so modern platforms can use them.

Which business systems does Procyon connect?

Commonly Salesforce, ServiceNow, SAP, Oracle, NetSuite, Workday, Snowflake, Databricks, Tableau, Slack and WhatsApp, plus custom and legacy systems.
